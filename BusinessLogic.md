# Бизнес-логика системы управления общежитием Dormitory

> Документ подготовлен на основе полного анализа кодовой базы, архитектурного плана и чеклиста проекта.
> Дата: 2026-03-11

---

## Общее описание продукта

Dormitory — коммерческая платформа для управления общежитием университета. Продукт заменяет бумажный учёт (тетради, Excel, заметки) и автоматизирует процессы заселения, проживания и оплаты.

Продукт развивается в **3 этапа**, каждый из которых расширяет аудиторию и функционал.

---

## Текущее состояние проекта (AS-IS)

Сейчас реализован минимальный прототип:

| Что есть | Состояние |
|----------|-----------|
| 3 модели: Student, Parent, Payment | Примитивные, не соответствуют бизнес-доменам |
| REST API: CRUD для 3 сущностей | Без пагинации, фильтрации, версионирования |
| JWT-аутентификация | Есть, но без ролей |
| Django Admin | Базовая регистрация моделей |
| База данных | SQLite (нужна PostgreSQL) |
| Тесты | Отсутствуют |
| Роли и права | Отсутствуют |

### Критичные проблемы текущей архитектуры

1. **Комната и этаж хранятся как числа в модели Student** — нет связи с реальными сущностями. Невозможно узнать, сколько мест свободно.
2. **Модель Payment не содержит сумму** — только булево поле "оплачено/не оплачено". Невозможно вести финансовый учёт.
3. **Нет модели Room/Building** — невозможно управлять фондом общежития.
4. **Нет истории проживания** — только текущий статус. При переселении старые данные теряются.
5. **Нет ролей** — любой аутентифицированный пользователь видит всё.
6. **Одно монолитное приложение `main`** — нет разделения по бизнес-доменам.

## 1.2 Бизнес-домены и сущности

### Домен: Организация (`organizations`)

**Зачем:** Даже если сейчас один университет — сущность Organization нужна для будущей продажи другим вузам.

#### Organization (Организация)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| name | string | Название организации ("Ташкентский университет") |
| type | enum | Тип (university, college, other) |
| status | enum | Статус (active, inactive) |
| contact_email | string | Email организации |
| contact_phone | string | Телефон организации |
| address | string | Адрес организации |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- Одна организация может иметь несколько корпусов общежитий
- Все данные в системе привязаны к организации (мульти-тенантность на уровне данных)
- При создании организации автоматически создаётся роль `university_admin`

### Домен: Инфраструктура общежития (`inventory`)

**Зачем:** Управление физической структурой — корпуса, этажи, комнаты, места. Замена полей `floor = IntegerField` и `room = IntegerField`.

#### Building (Корпус)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| organization | FK → Organization | Привязка к организации |
| name | string | Название ("Корпус A", "Общежитие №3") |
| address | string | Адрес |
| total_floors | int | Количество этажей |
| gender_policy | enum | Политика (male_only, female_only, mixed) |
| is_active | bool | Активен ли корпус |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- Корпус принадлежит одной организации
- В корпусе есть этажи, на этажах — комнаты
- При деактивации корпуса — нельзя заселять новых жильцов

#### Floor (Этаж)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| building | FK → Building | Привязка к корпусу |
| number | int | Номер этажа |
| description | string | Описание (опционально) |

**Бизнес-правила:**
- Этаж принадлежит одному корпусу
- Номера этажей уникальны в рамках корпуса

#### Room (Комната)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| floor | FK → Floor | Привязка к этажу |
| room_number | string | Номер комнаты ("101", "205A") |
| capacity | int | Вместимость (количество мест) |
| current_occupancy | int (вычисляемое) | Текущее количество жильцов |
| gender_policy | enum | Политика (male, female, mixed) |
| status | enum | Статус (available, full, maintenance, closed) |
| monthly_price | decimal | Стоимость проживания в месяц |
| description | string | Описание (опционально) |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- `current_occupancy` вычисляется из активных RoomAssignment
- `status` автоматически переходит в `full`, когда `current_occupancy == capacity`
- `status` автоматически переходит в `available`, когда появляется свободное место
- Нельзя заселить жильца, если `current_occupancy >= capacity`
- Нельзя заселить мужчину в комнату с `gender_policy = female` и наоборот
- Номер комнаты уникален в рамках этажа

#### Вычисляемые показатели инфраструктуры

| Показатель | Формула | Уровень |
|------------|---------|---------|
| Свободные места в комнате | capacity - current_occupancy | Room |
| Свободные места на этаже | SUM(свободные места всех комнат этажа) | Floor |
| Свободные места в корпусе | SUM(свободные места всех этажей) | Building |
| Общая вместимость корпуса | SUM(capacity всех комнат) | Building |
| Процент занятости | (занято / вместимость) × 100% | Building / Floor |

### Домен: Жильцы (`residents`)

**Зачем:** Полная анкета жильца, данные родителей, документы. Замена текущей модели Student.

#### Resident (Жилец)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| organization | FK → Organization | Привязка к организации |
| full_name | string(150) | ФИО |
| birth_date | date | Дата рождения |
| gender | enum | Пол (male, female) |
| phone_number | string(15) | Телефон (с валидацией) |
| email | string | Email (опционально) |
| university_id | string | Номер студенческого билета |
| faculty | string | Факультет |
| course | int | Курс |
| photo | image | Фото жильца |
| status | enum | Статус (active, evicted, graduated, suspended) |
| registration_date | date | Дата первой регистрации в системе |
| notes | text | Заметки администрации |
| created_at | datetime | Дата создания записи |
| updated_at | datetime | Дата обновления |

**Бизнес-правила:**
- Жилец принадлежит одной организации
- `university_id` уникален в рамках организации
- Жилец НЕ хранит напрямую комнату/этаж — это делает RoomAssignment
- Статус `active` = проживает сейчас (есть активный RoomAssignment)
- Статус `evicted` = выселен (все RoomAssignment закрыты)
- Статус `graduated` = выпустился
- Статус `suspended` = временно отстранён
- При смене статуса на `evicted` или `graduated` — все активные назначения автоматически закрываются

#### Guardian (Родитель / Опекун)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| resident | FK → Resident | Привязка к жильцу |
| full_name | string(150) | ФИО |
| relationship | enum | Тип связи (father, mother, guardian, other) |
| phone_number | string(15) | Телефон |
| address | string | Адрес (опционально) |
| is_emergency_contact | bool | Экстренный контакт? |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- У жильца может быть несколько родителей/опекунов (ForeignKey, не OneToOne как сейчас)
- Хотя бы один Guardian должен быть отмечен как `is_emergency_contact`
- При удалении жильца — удаляются все связанные Guardian

#### ResidentDocument (Документ жильца)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| resident | FK → Resident | Привязка к жильцу |
| document_type | enum | Тип (passport, student_id, contract, medical, other) |
| document_number | string | Номер документа |
| file | file | Скан / фото документа |
| uploaded_at | datetime | Дата загрузки |

**Бизнес-правила:**
- Один жилец может иметь несколько документов разных типов
- Фото паспорта и студенческого — отдельные документы, а не поля в модели жильца (как сейчас)
- Файлы хранятся с возможностью миграции на облачное хранилище

### Домен: Проживание (`occupancy`)

**Зачем:** Жизненный цикл проживания — от заселения до выселения. Замена полей `arrival_date`, `departure_date`, `status` в текущей модели Student.

#### AccommodationContract (Договор проживания)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| resident | FK → Resident | Жилец |
| building | FK → Building | Корпус |
| contract_number | string | Номер договора (автогенерация) |
| start_date | date | Дата начала |
| end_date | date | Дата окончания |
| status | enum | Статус (active, expired, terminated, draft) |
| signed_at | datetime | Дата подписания |
| terminated_at | datetime | Дата расторжения (если есть) |
| termination_reason | string | Причина расторжения |
| created_by | FK → User | Кто создал |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- У жильца может быть только ОДИН активный договор одновременно
- `end_date` > `start_date`
- При истечении `end_date` статус автоматически → `expired`
- При ручном расторжении заполняется `terminated_at` и `termination_reason`
- Расторжение договора → закрытие всех активных RoomAssignment
- Номер договора генерируется: `{ORG_CODE}-{YEAR}-{SEQUENCE}`

#### RoomAssignment (Назначение комнаты)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| contract | FK → AccommodationContract | Привязка к договору |
| resident | FK → Resident | Жилец |
| room | FK → Room | Комната |
| start_date | date | Дата заселения |
| end_date | date | Дата выселения (null = проживает) |
| status | enum | Статус (active, completed, cancelled) |
| assigned_by | FK → User | Кто назначил |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- У жильца может быть только ОДНО активное назначение одновременно
- Перед назначением — проверка: `room.current_occupancy < room.capacity`
- Перед назначением — проверка гендерной политики комнаты
- Перед назначением — проверка: у жильца есть активный договор
- При создании назначения — `room.current_occupancy += 1`
- При закрытии назначения — `room.current_occupancy -= 1`
- `end_date = null` означает, что жилец всё ещё живёт

#### StayRecord (Запись о пребывании)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| resident | FK → Resident | Жилец |
| check_in_at | datetime | Дата/время заезда |
| check_out_at | datetime | Дата/время выезда (null = проживает) |
| reason | enum | Причина (initial_check_in, return, transfer, eviction, graduation) |
| notes | text | Заметки |
| recorded_by | FK → User | Кто зафиксировал |

**Бизнес-правила:**
- Фиксирует фактическое физическое присутствие
- Используется охраной / комендантом
- Один жилец может иметь множество записей (уехал на каникулы → вернулся)

### Бизнес-процессы проживания

#### Процесс: Заселение нового жильца

```
1. Комендант создаёт анкету жильца (Resident) → статус: active
2. Комендант добавляет родителя/опекуна (Guardian)
3. Комендант загружает документы (ResidentDocument)
4. Комендант создаёт договор (AccommodationContract) → статус: active
5. Комендант назначает комнату (RoomAssignment) → статус: active
   → Система проверяет: есть ли место в комнате
   → Система проверяет: гендерная политика
   → Система обновляет: room.current_occupancy += 1
   → Система обновляет: room.status (если заполнена → full)
6. Комендант фиксирует заезд (StayRecord) → reason: initial_check_in
7. Бухгалтер создаёт начисление (Charge) за первый месяц
```

#### Процесс: Выселение жильца

```
1. Комендант инициирует выселение
2. Система проверяет: есть ли задолженность
   → Если есть — предупреждение (но не блокировка)
3. Комендант закрывает RoomAssignment → end_date = today, status: completed
   → Система обновляет: room.current_occupancy -= 1
   → Система обновляет: room.status (если было full → available)
4. Комендант расторгает договор → status: terminated
5. Комендант фиксирует выезд (StayRecord) → reason: eviction
6. Жилец → status: evicted
```

#### Процесс: Перевод в другую комнату

```
1. Комендант инициирует перевод
2. Система проверяет: есть ли место в новой комнате
3. Закрытие текущего RoomAssignment → end_date = today, status: completed
   → room_old.current_occupancy -= 1
4. Создание нового RoomAssignment → start_date = today, status: active
   → room_new.current_occupancy += 1
5. Фиксация StayRecord → reason: transfer
```

### Домен: Финансы (`billing`)

**Зачем:** Учёт тарифов, начислений, оплат и долгов. Замена текущей модели Payment (которая не содержит сумму).

#### TariffPlan (Тарифный план)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| organization | FK → Organization | Привязка к организации |
| name | string | Название ("Стандартный", "Льготный") |
| amount | decimal(10,2) | Сумма за период |
| billing_period | enum | Период (monthly, quarterly, semester, yearly) |
| is_active | bool | Активен ли тариф |
| description | text | Описание |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- Организация может иметь несколько тарифов
- Тариф привязывается к договору или назначается жильцу
- Неактивный тариф нельзя назначать новым жильцам

#### Charge (Начисление)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| resident | FK → Resident | Жилец |
| tariff_plan | FK → TariffPlan | Тариф |
| period_month | int | Месяц начисления (1-12) |
| period_year | int | Год начисления |
| amount | decimal(10,2) | Сумма начисления |
| status | enum | Статус (pending, partially_paid, paid, cancelled, overdue) |
| due_date | date | Крайний срок оплаты |
| created_at | datetime | Дата создания |
| created_by | FK → User | Кто создал |

**Бизнес-правила:**
- Одно начисление = один период (месяц) для одного жильца
- Нельзя создать дублирующее начисление за тот же период
- `status = pending` при создании
- `status = overdue` если `due_date` прошла и `status` ещё `pending`
- `status = partially_paid` если оплачена часть суммы
- `status = paid` если оплачена полная сумма
- `status = cancelled` при отмене начисления
- Начисление может быть создано вручную бухгалтером или автоматически по тарифу

#### Payment (Оплата)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| resident | FK → Resident | Жилец |
| amount | decimal(10,2) | Сумма оплаты |
| payment_date | date | Дата оплаты |
| payment_method | enum | Способ (cash, bank_transfer, card, online) |
| status | enum | Статус (confirmed, pending, cancelled) |
| receipt_number | string | Номер квитанции |
| external_reference | string | Внешний номер (для онлайн-оплаты — Этап 3) |
| notes | text | Заметки |
| recorded_by | FK → User | Кто внёс запись |
| created_at | datetime | Дата создания |

**Бизнес-правила (Этап 1 — ручной ввод):**
- Бухгалтер вносит оплату вручную после получения денег
- `payment_method` на Этапе 1: только `cash` и `bank_transfer`
- `status = confirmed` сразу при ручном вводе
- При создании оплаты — автоматическое распределение по неоплаченным начислениям (PaymentAllocation)

#### PaymentAllocation (Распределение оплаты)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| payment | FK → Payment | Оплата |
| charge | FK → Charge | Начисление |
| amount | decimal(10,2) | Распределённая сумма |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- Одна оплата может покрывать несколько начислений
- Одно начисление может быть оплачено несколькими оплатами
- `SUM(allocations.amount)` для Payment не может превышать `payment.amount`
- `SUM(allocations.amount)` для Charge не может превышать `charge.amount`
- Распределение идёт автоматически: сначала самые старые неоплаченные начисления

#### Discount (Скидка)
| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Уникальный идентификатор |
| resident | FK → Resident | Жилец |
| type | enum | Тип (percentage, fixed_amount) |
| value | decimal | Значение (процент или сумма) |
| reason | string | Причина скидки |
| start_date | date | Начало действия |
| end_date | date | Конец действия |
| is_active | bool | Активна ли |
| approved_by | FK → User | Кто одобрил |

**Бизнес-правила:**
- Скидка применяется при создании начисления
- Скидка может быть процентной или фиксированной
- Скидку может одобрить только `university_admin` или `platform_admin`

### Бизнес-процессы финансов (Этап 1)

#### Процесс: Ежемесячное начисление

```
1. Бухгалтер (или система автоматически) создаёт начисления за месяц
   → Для каждого жильца с активным договором:
     → amount = тариф.amount - скидка (если есть)
     → due_date = последний день месяца
     → status = pending
2. Если начисление не оплачено после due_date → status = overdue
3. Формируется список должников
```

#### Процесс: Ручной ввод оплаты

```
1. Студент приносит деньги в кассу / делает банковский перевод
2. Бухгалтер открывает систему → находит жильца
3. Бухгалтер создаёт Payment:
   → amount = полученная сумма
   → payment_method = cash / bank_transfer
   → payment_date = сегодня
4. Система автоматически создаёт PaymentAllocation:
   → Берёт самые старые неоплаченные Charge
   → Распределяет сумму по начислениям
   → Обновляет статусы Charge (paid / partially_paid)
5. Если сумма оплаты > суммы всех долгов → остаток = переплата (кредит на будущее)
```

#### Формула расчёта задолженности

```
Задолженность жильца = SUM(charges.amount WHERE status IN (pending, overdue, partially_paid))
                     - SUM(allocations.amount WHERE charge IN (те же начисления))
```

## 3.3 Процесс онлайн-оплаты

```
1. Студент открывает приложение → раздел "Оплата"
2. Видит список неоплаченных начислений (Charges)
3. Выбирает начисления для оплаты
4. Выбирает способ оплаты (Payme / Click / карта)
5. Система создаёт OnlinePaymentTransaction → status: initiated
6. Студент перенаправляется на страницу платёжного провайдера
   (или провайдер открывается в WebView)
7. Студент вводит данные карты / подтверждает оплату
8. Провайдер обрабатывает платёж:
   → Успех: webhook → status: completed
   → Неудача: webhook → status: failed
9. При УСПЕХЕ:
   a. OnlinePaymentTransaction → status: completed
   b. Создаётся Payment → payment_method: online, status: confirmed
   c. Создаются PaymentAllocation (распределение по начислениям)
   d. Обновляются статусы Charge (paid / partially_paid)
   e. Создаётся PaymentReceipt
   f. Отправляется уведомление студенту: "Оплата {сумма} подтверждена"
10. При НЕУДАЧЕ:
    a. OnlinePaymentTransaction → status: failed
    b. Уведомление студенту: "Оплата не прошла: {причина}"
    c. Студент может повторить попытку
```

## 3.4 Webhook-обработка

#### Webhooks от платёжных провайдеров

| Endpoint | Провайдер | Описание |
|----------|-----------|----------|
| POST `/api/v1/webhooks/payme/` | Payme | Callback от Payme |
| POST `/api/v1/webhooks/click/` | Click | Callback от Click |

**Бизнес-правила обработки webhook:**

2. Проверка: транзакция с таким `provider_transaction_id` существует?
3. Проверка: статус транзакции позволяет обновление? (идемпотентность)
4. Обновление статуса транзакции

| id | UUID | Уникальный идентификатор |
| provider | FK → PaymentProvider | Провайдер |
| period_start | date | Начало периода |
| period_end | date | Конец периода |
| total_transactions | int | Всего транзакций |
| total_amount | decimal | Общая сумма |
| matched | int | Совпадают |
| mismatched | int | Расхождения |
| status | enum | Статус (pending, completed, has_issues) |
| report | JSON | Детализация |
| created_at | datetime | Дата создания |

**Бизнес-правила:**
- Ежедневная/еженедельная сверка с провайдером
- При расхождении — уведомление бухгалтеру
- Бухгалтер вручную разрешает расхождения
