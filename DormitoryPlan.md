# План Архитектуры Dormitory

## Направление продукта

Этот продукт должен строиться как коммерческая платформа для управления общежитием.

Этап 1: внутренняя веб-платформа для администрации университета. Она заменяет тетради, заметки, Excel и ручной учет. На этом этапе системой пользуются только сотрудники университета.

Этап 2: мобильное приложение для студентов. Студенты смогут видеть свой статус проживания, свободные комнаты и информацию по оплатам.

Этап 3: подключение онлайн-оплаты, чтобы студенты могли платить внутри платформы.

Архитектура должна поддерживать этот путь развития без полного переписывания системы в будущем.

## Стратегия разработки

Стартовать нужно с модульного монолита на Django и Django REST Framework.

Почему это правильный вариант:
- быстрое создание MVP
- более простой деплой
- более простая поддержка маленькой командой
- достаточно гибкости для роста в коммерческий продукт

На текущем этапе микросервисы не нужны.

## Этапы продукта

### Этап 1: Административная платформа

Основные пользователи:
- администрация университета
- коменданты
- бухгалтерия
- охрана или сотрудники на входе

Основные цели:

- вести учет комнат и занятости

### Этап 2: Мобильное приложение для студентов

Новые возможности:
- вход студента в систему
- просмотр личного профиля
- просмотр своей комнаты
- просмотр свободных комнат
- просмотр истории оплат
- просмотр задолженности
- получение уведомлений

### Этап 3: Онлайн-оплата

Новые возможности:
- интеграция с платежной системой

- подтверждение платежей

## Базовая архитектура

Система должна строиться не вокруг одной модели `Student`, а вокруг бизнес-доменов общежития.

Рекомендуемый стиль backend-архитектуры:
- модульный монолит
- REST API с версионированием
- модель данных, готовая к PostgreSQL
- ролевая система прав
- бизнес-логика по модулям внутри Django apps

Рекомендуемый префикс API:
- `/api/v1/...`

## Основные модули системы

### 1. accounts

Назначение:
- аутентификация
- JWT-токены
- роли пользователей
- права сотрудников
- будущие аккаунты студентов

Основные сущности:
- `User`
- `Role`
- `UserProfile`

### 2. organizations

Назначение:
- представление университета или будущего клиента
- подготовка системы к коммерческому расширению

Основные сущности:
- `Organization`
- `Campus`
- `DormitoryBuilding`

Важно:
Даже если первый запуск будет только для одного университета, сущность `Organization` нужно заложить сразу. Это позволит в будущем продавать систему другим организациям без полной переделки.

### 3. residents

Назначение:
- анкеты жильцов
- данные родителей или опекунов
- документы
- контактная информация

Основные сущности:
- `Resident`
- `Guardian`
- `ResidentDocument`
- `EmergencyContact`

### 4. inventory

Назначение:
- физическая структура общежития
- учет комнат
- учет свободных мест

Основные сущности:
- `Building`
- `Floor`
- `Room`
- `BedSpace`

Если для MVP будет слишком тяжело вводить койко-места, можно начать с `Room.capacity`, а `BedSpace` добавить позже.

### 5. occupancy

Назначение:
- жизненный цикл проживания
- заселение и выселение
- история перемещений
- договоры проживания

Основные сущности:
- `AccommodationContract`
- `StayRecord`
- `RoomAssignment`
- `TransferRecord`

Этот модуль критичен. Жилец не должен напрямую хранить `room` и `floor` как простые поля, как это сделано сейчас.

### 6. billing

Назначение:
- тарифы
- начисления
- оплаты
- долги
- скидки

Основные сущности:
- `TariffPlan`
- `Charge`
- `Payment`
- `PaymentAllocation`
- `Discount`

Этот модуль должен поддерживать и ручной ввод оплат сейчас, и онлайн-оплату позже.

### 7. requests

Назначение:
- заявки на ремонт
- жалобы
- внутренние обращения

Основные сущности:
- `SupportRequest`
- `RequestComment`
- `RequestAttachment`

Этот модуль можно добавить после первого этапа.

### 8. notifications

Назначение:
- напоминания
- уведомления о долгах
- уведомления о заселении
- уведомления о платежах

Основные сущности:
- `Notification`
- `NotificationTemplate`
- `DeliveryLog`

### 9. reports

Назначение:
- отчеты по занятости
- отчеты по долгам
- отчеты по оплатам
- статистика использования комнат

### 10. audit

Назначение:
- хранить историю изменений
- понимать, кто и что изменил
- поддерживать прозрачность для коммерческого продукта

Основная сущность:
- `AuditLog`

## Роли и права

Роли для Этапа 1:
- `platform_admin`
- `university_admin`
- `dorm_manager`
- `accountant`
- `security_staff`

Дополнительная роль для Этапа 2:
- `student`

Модель прав должна быть ролевой и, при необходимости, объектной.

Примеры:
- бухгалтер управляет оплатами и начислениями
- комендант управляет комнатами и заселением
- охрана видит проживание, но не видит финансы
- студент видит только свои данные

## Правила проектирования данных

Эти правила должны быть базовыми при переписывании:

1. Нельзя хранить важные бизнес-связи как простой текст, если это реальные сущности.
2. Жилец не должен напрямую хранить `room` и `floor` как примитивные поля.
3. У записи оплаты обязательно должны быть сумма и учетные атрибуты.
4. Проживание должно храниться исторически, а не только как текущее состояние.
5. Каждая важная сущность должна быть готова к связи с организацией.
6. Файлы вроде фото паспорта должны храниться так, чтобы позже можно было перейти на облачное хранилище.

## MVP-архитектура под ваш текущий план

Так как ближайшая цель это одна административная платформа для одного университета, MVP должен содержать только нужные сейчас модули, но быть готовым к расширению.

### Модули MVP
- `accounts`
- `organizations`
- `residents`
- `inventory`
- `occupancy`
- `billing`
- `reports`
- `audit`

### Возможности MVP
- вход сотрудников
- управление жильцами
- управление родителями или опекунами
- управление корпусами, этажами и комнатами
- учет занятости комнат
- учет договоров
- ручной ввод оплат
- расчет задолженности
- отчеты для администрации

### Отложенные, но запланированные возможности
- мобильный вход студентов
- просмотр свободных комнат студентами
- онлайн-оплата
- уведомления
- заявки и обращения

## Принципы коммерческой готовности

Если продукт должен продаваться в будущем, эти принципы нельзя нарушать:

- система должна быть готова к работе с организациями с самого начала
- проживание и биллинг должны быть отдельными доменами
- API не должен быть привязан только к одной frontend-части
- чувствительные операции должны быть аудируемыми
- данные должны храниться исторически, чтобы отчеты не ломались
- аутентификация, доменная логика и финансы должны быть разделены

## Ближайшая правильная задача

Следующий шаг это не случайная правка кода.

Правильный следующий шаг:
1. зафиксировать новую структуру проекта
2. утвердить первые стабильные модели для организации, пользователей, комнат, жильцов, заселения и финансов
3. затем переписывать проект модуль за модулем

Этот план дает фундамент для:
- административной платформы уже сейчас
- мобильного приложения для студентов позже
- онлайн-оплаты позже
- коммерческого расширения в будущем
