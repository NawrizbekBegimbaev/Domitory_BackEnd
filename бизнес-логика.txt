                  DORMITORY - БИЗНЕС-ЛОГИКА СИСТЕМЫ

Документ описывает все бизнес-правила, алгоритмы расчётов,
ограничения и потоки данных в системе.

1. МОДЕЛЬ ДАННЫХ
================================================================================

--------------------------------------------------------------------------------
1.1. Иерархия сущностей
--------------------------------------------------------------------------------

  Корпус (Building)
    └── Этаж (Floor)
         └── Комната (Room)

  Жилец (Resident)
    ├── Опекуны (Guardian)
    ├── Документы (ResidentDocument)
    ├── Договор (AccommodationContract)
    │    └── Назначение комнаты (RoomAssignment)
    ├── Начисления (Charge)
    ├── Платежи (Payment)
    │    └── Распределения (PaymentAllocation)
    └── События доступа (AccessEvent)

  Пользователь (User)
    └── Роль (Role)

  Аудит (AuditLog) — логирует все действия всех сущностей.
  История проживания (StayRecord) — логирует перемещения жильцов.

--------------------------------------------------------------------------------
1.2. Уникальные ограничения
--------------------------------------------------------------------------------

  User.email             — уникален
  User.phone_number      — уникален (null допустим)
  User.telegram_id       — уникален (null допустим)
  Floor (building, number) — уникальная пара
  Room (floor, room_number) — уникальная пара
  AccommodationContract.contract_number — уникален
  Charge (resident, period_month, period_year, room) — уникальная четвёрка
  PaymentAllocation (payment, charge) — уникальная пара

================================================================================
2. ЗАСЕЛЕНИЕ
================================================================================

--------------------------------------------------------------------------------
2.1. Обычное заселение (1 место)
--------------------------------------------------------------------------------

Вход:
  - resident: жилец
  - room: комната
  - contract: активный договор
  - beds_purchased: 1 (по умолчанию)

Валидации:
  1. У жильца нет активного назначения
  2. Договор в статусе ACTIVE
  3. В комнате есть свободные места:
     room.current_occupancy + beds_purchased <= room.capacity
  4. Гендерная политика:
     - Проверяется на уровне корпуса (building.gender_policy)
     - Проверяется на уровне комнаты (room.gender_policy)
     - Мужчина не может в женскую комнату и наоборот
     - В смешанную (mixed) — можно любому

Действия:
  1. Создать RoomAssignment (status=ACTIVE, beds_purchased=1)
  2. room.current_occupancy += 1
  3. Если occupancy >= capacity → room.status = FULL
  4. Создать StayRecord (reason=INITIAL_CHECK_IN)
  5. resident.status = ACTIVE
  6. Генерировать начисления на весь период договора
  7. Запустить FIFO-распределение платежей
  8. Записать аудит

--------------------------------------------------------------------------------
2.2. Покупка всей комнаты (групповое заселение)
--------------------------------------------------------------------------------

Вход:
  - residents_and_contracts: список пар (жилец, договор)
  - room: комната (должна быть пустой)

Валидации:
  1. Комната пустая (current_occupancy = 0)
  2. Все договоры ACTIVE
  3. Ни у кого нет активного назначения

Расчёт:
  total_cost = room.monthly_price x room.capacity
  per_person = total_cost / количество_жильцов
  beds_each  = room.capacity // количество_жильцов
  remainder  = room.capacity % количество_жильцов

  Остаток (remainder) распределяется по одному первым жильцам в списке.

Пример:
  Комната: 4 места, 500 000/место
  Жильцы: 3 человека
  total_cost = 500 000 x 4 = 2 000 000
  per_person = 666 667
  beds_each = 1 (4 // 3)
  remainder = 1 (4 % 3)
  → Жилец 1: 2 места, платит 666 667
  → Жилец 2: 1 место, платит 666 667
  → Жилец 3: 1 место, платит 666 667

Действия:
  Для каждого жильца:
    1. Создать RoomAssignment (beds_purchased = распределённое кол-во)
    2. room.current_occupancy += beds_purchased
  3. room.status = FULL
  4. Генерировать начисления (price = per_person)
  5. FIFO-распределение
  6. StayRecord + аудит

================================================================================
3. ВЫСЕЛЕНИЕ
================================================================================

Вход:
  - assignment: активное назначение комнаты

Действия:
  1. assignment.status = COMPLETED
  2. assignment.end_date = сегодня
  3. room.current_occupancy -= assignment.beds_purchased
  4. Если occupancy < capacity → room.status = AVAILABLE
  5. Расторгнуть договор (ContractService.terminate_contract)
  6. resident.status = EVICTED
  7. Создать StayRecord (reason=EVICTION)

Важно: если в комнате были жильцы с beds_purchased > 1
(групповая покупка), после выселения одного:
  - Все оставшиеся пересчитываются на 1 место каждый
  - Начисления пересчитываются по стандартной цене

================================================================================
4. РАСТОРЖЕНИЕ ДОГОВОРА
================================================================================

Вход:
  - contract: договор

Действия:
  1. contract.status = TERMINATED
  2. Закрыть все активные назначения:
     - assignment.status = COMPLETED
     - assignment.end_date = сегодня
     - Освободить места в комнатах
     - Пересчитать группы (если были beds_purchased > 1)
  3. Пересчёт финансов (_refund_on_termination):

     Текущий месяц:
       - Рассчитать пропорциональную сумму за фактические дни
       - start_day = 1, end_day = сегодня.день
       - new_amount = (price / дней_в_месяце) x end_day
       - Обновить начисление
       - Удалить PaymentAllocation для этого начисления
       - Пометить is_prorated = True

     Будущие месяцы:
       - Все начисления → status = CANCELLED
       - Удалить все PaymentAllocation для этих начислений

     Перераспределение:
       - Запустить полный FIFO заново

  4. resident.status = EVICTED
  5. Записать аудит

================================================================================
5. ПЕРЕВОД В ДРУГУЮ КОМНАТУ
================================================================================

Вход:
  - assignment: текущее назначение
  - new_room: новая комната

Валидации:
  - Новая комната имеет свободные места
  - Гендерная политика совпадает

Действия:
  1. Закрыть старое назначение:
     - status = TRANSFERRED
     - end_date = сегодня

  2. Освободить места в старой комнате:
     - old_room.current_occupancy -= beds_purchased
     - Обновить статус комнаты

  3. Пересчёт группы в старой комнате:
     - Если кто-то из оставшихся имел beds_purchased > 1:
       сбросить всем beds_purchased = 1, пересчитать начисления

  4. Создать новое назначение:
     - new_room, beds_purchased = 1
     - new_room.current_occupancy += 1

  5. Пересчёт начислений:

     Текущий месяц — старая комната:
       - Пропорционально: день 1 → (день_перевода - 1)
       - Если день_перевода = 1 → отменить начисление
       - Формула: (old_price / дней_в_месяце) x дней_в_старой

     Текущий месяц — новая комната:
       - Пропорционально: день_перевода → конец_месяца
       - Формула: (new_price / дней_в_месяце) x дней_в_новой

     Будущие месяцы:
       - Отменить начисления по старой цене
       - Создать новые по цене новой комнаты

  6. Перераспределить платежи (FIFO)
  7. StayRecord (reason=TRANSFER)
  8. Аудит

================================================================================
6. НАЧИСЛЕНИЯ (CHARGES)
================================================================================

--------------------------------------------------------------------------------
6.1. Автоматическая генерация
--------------------------------------------------------------------------------

Запускается при заселении. Создаёт начисления на каждый месяц
от начала до конца договора.

Для каждого месяца:
  - start_day: день начала (первый месяц — день заселения, остальные — 1)
  - end_day: день конца (последний месяц — день выселения, остальные — последний день месяца)
  - days_charged: end_day - start_day + 1
  - is_prorated: true если неполный месяц

Расчёт суммы:
  Полный месяц: monthly_price (или price_override для групповых)
  Неполный месяц: (monthly_price / дней_в_месяце) x days_charged

Округление: ROUND_HALF_UP (математическое округление)

Срок оплаты (due_date): 25-е число месяца начисления.
Если в месяце < 25 дней — последний день месяца.

--------------------------------------------------------------------------------
6.2. Статусы начислений
--------------------------------------------------------------------------------

  PENDING        — ожидает оплаты (начальный статус)
  PARTIALLY_PAID — часть суммы оплачена
  PAID           — полностью оплачен
  OVERDUE        — просрочен (после due_date)
  CANCELLED      — отменён (при расторжении/переводе)

--------------------------------------------------------------------------------
6.3. Уникальность
--------------------------------------------------------------------------------

Одно начисление на жильца за один месяц в одной комнате:
  (resident, period_month, period_year, room)

При переводе в том же месяце — два начисления: за старую и новую комнату.

================================================================================
7. ПЛАТЕЖИ И FIFO-РАСПРЕДЕЛЕНИЕ
================================================================================

--------------------------------------------------------------------------------
7.1. Создание платежа
--------------------------------------------------------------------------------

Вход:
  - resident: жилец
  - amount: сумма
  - payment_method: наличные / банковский перевод
  - payment_date: дата платежа
  - recorded_by: кто принял

Действия:
  1. Создать Payment (status=COMPLETED)
  2. Получить все неоплаченные начисления жильца,
     отсортированные по: period_year, period_month, start_day (ASC)
  3. Распределить сумму по FIFO:

     remaining = amount
     для каждого charge (от старого к новому):
       allocation = min(remaining, charge.remaining)
       создать PaymentAllocation(payment, charge, allocation)
       если charge полностью оплачен → status = PAID
       если частично → status = PARTIALLY_PAID
       remaining -= allocation
       если remaining = 0 → стоп

  4. Записать аудит

--------------------------------------------------------------------------------
7.2. Полное перераспределение (reallocate_all_payments)
--------------------------------------------------------------------------------

Вызывается при изменении начислений (перевод, расторжение).

Алгоритм:
  1. Удалить ВСЕ PaymentAllocation для жильца
  2. Сбросить все начисления в PENDING (кроме CANCELLED)
  3. Получить все COMPLETED платежи, отсортированные по дате
  4. Для каждого платежа → распределить по FIFO (как при создании)

Это гарантирует корректное состояние после любых изменений.

--------------------------------------------------------------------------------
7.3. Баланс жильца
--------------------------------------------------------------------------------

  total_charges = сумма всех активных начислений
  total_paid    = сумма всех платежей
  debt          = total_charges - total_paid

================================================================================
8. ОТЧЁТЫ
================================================================================

  1. Сводка (summary)
     - total_residents: количество жильцов со статусом ACTIVE
     - free_beds: сумма (capacity - current_occupancy) по всем комнатам
     - total_debt: сумма неоплаченных начислений (PENDING + PARTIALLY_PAID + OVERDUE)
     - collected_this_month: сумма платежей за текущий месяц

  2. Заполняемость (occupancy)
     - По каждому корпусу → по каждому этажу:
       capacity, occupancy, free, percentage

  3. Свободные комнаты (available-rooms)
     - Фильтр по корпусу и полу
     - Показывает: номер, вместимость, свободные места, цену

  4. Должники (debtors)
     - Жильцы с задолженностью > 0
     - Поля: ФИО, студ. ID, факультет, телефон, начислено, оплачено, долг
     - Сортировка: по долгу (от большего к меньшему)

  5. Платежи (payments)
     - Фильтр: дата от/до, способ оплаты
     - Возвращает: список платежей, общая сумма, количество

  6. Жильцы (residents)
     - Фильтр: статус, факультет, пол
     - Полный список с основными полями

9. КОНТРОЛЬ ДОСТУПА
================================================================================

Модель: AccessEvent
  - resident: жилец (FK)
  - direction: IN (вход) / OUT (выход)
  - timestamp: время события
  - device_name: название устройства (турникет, дверь)
  - card_number: номер карты доступа

API:
  GET  /api/v1/access-events/     — журнал событий (пагинация, фильтры)
  POST /api/v1/access-events/     — создание события (от внешней системы)

Фильтры: resident, direction, device_name, date_from, date_to
Поиск: ФИО жильца, устройство, номер карты

Интеграция с Hikvision:
  - Вариант 1: Hik-Connect Cloud API → прямые запросы на наш endpoint
  - Вариант 2: Локальный агент (скрипт на ПК в сети университета)
  - Вариант 3: Университет сам пушит данные на наш API

10. АУДИТ
================================================================================

Модель: AuditLog

Записывается при каждом критическом действии:
  - user: кто выполнил
  - action: CREATE / UPDATE / DELETE
  - model_name: какая сущность (Resident, Payment, Contract...)
  - object_id: ID объекта
  - changes: JSON с изменениями {поле: {old: ..., new: ...}}
  - ip_address: IP пользователя
  - timestamp: время

Что логируется:
  - Создание/редактирование/удаление жильцов
  - Создание/расторжение договоров
  - Назначение/закрытие комнат
  - Все платежи
  - Изменения начислений
  - Переводы между комнатами
  - Выселения

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

  3. Генерирует OTP-код
  4. Отправляет через Telegram Bot API

  6. Система проверяет и выдаёт JWT

12. ВАЛИДАЦИИ И БИЗНЕС-ПРАВИЛА
================================================================================

Комнаты:
  - current_occupancy <= capacity (всегда)
  - Гендерная политика проверяется при заселении
  - Статус обновляется автоматически (AVAILABLE ↔ FULL)

Договоры:
  - end_date > start_date
  - Только ACTIVE договор может иметь назначения
  - Один жилец — один активный договор

Назначения:
  - Один жилец — одно активное назначение
  - beds_purchased >= 1

Начисления:
  - Одно на жильца за месяц в комнате
  - Пропорциональные за неполные месяцы
  - Отменяются при расторжении будущих периодов

Платежи:
  - Распределяются только по FIFO (от старых к новым)
  - PaymentAllocation — один на пару (платёж, начисление)
  - При изменении начислений — полное перераспределение

Пользователи:
  - Email уникален
  - Телефон уникален (если указан)
  - Telegram ID уникален (если указан)

================================================================================
13. ЦЕЛОСТНОСТЬ ДАННЫХ
================================================================================

Транзакции:
  - Все критические операции обёрнуты в @transaction.atomic
  - Заселение, выселение, перевод, расторжение, платежи

Каскадное удаление:
  - Жилец удалён → удаляются опекуны, документы, события доступа
  - Платёж удалён → удаляются распределения

Защита от удаления:
  - Роль не удаляется если есть пользователи (PROTECT)

Индексы для производительности:
  - AuditLog: (model_name, object_id), timestamp
  - AccessEvent: (resident, -timestamp), (direction, -timestamp)
  - Charge: (resident, period_month, period_year, room)
  - Payment: payment_date

15. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ
================================================================================

  1. Fat Services, Thin Views
     Вся бизнес-логика в services.py.
     Views только: принять запрос → вызвать сервис → вернуть ответ.

  2. Single-tenant
     Все данные в одном пространстве. Нет фильтрации по организации.

  3. FIFO-оплата
     Платёж всегда идёт на самое старое неоплаченное начисление.

  4. Автоматические начисления
     При заселении создаются на весь период. При изменениях — пересчёт.

  5. Аудит всего критического
     Любое изменение финансов, проживания, договоров — в логе.
